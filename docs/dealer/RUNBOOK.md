# Runbook

Operational procedures for Dealer Rewards. Written for whoever is on the other
end of the phone when a dealer or a customer says something is wrong.

**The rule that decides ties:** the sale record is the product. When you are
choosing between two actions, prefer the one that keeps an accurate record of
when a mattress was sold. Points can always be corrected with a ledger entry; a
warranty start date that nobody can defend cannot be.

---

## 1. First deploy

1. **Create the blueprint.** Render Dashboard → New → Blueprint → select this
   repo → Apply. It creates four resources: `dealerrewards-api`,
   `dealerrewards-db`, `dealerrewards-redis`, `dealerrewards-unit-sync`.

2. **Check the database backups before anything else.** Dashboard → Database →
   Backups. Daily backups must be listed. If they are not, upgrade the instance
   type until they are and re-apply. This database is the only record of
   five-year warranty obligations; there is no upstream copy to restore from.

3. **Fill in the dashboard secrets.** Everything marked `sync: false` in
   `render.yaml` is blank until you set it:

   | Variable | Where it comes from |
   |---|---|
   | `CORS_ORIGINS` | admin-web and support-web URLs, comma separated |
   | `PUBLIC_BASE_URL` | support-web URL — it goes into every customer SMS |
   | `SMS_SENDER_ID`, `MSG91_AUTH_KEY`, `MSG91_*_TEMPLATE_ID` | MSG91 dashboard, after DLT approval |
   | `GBREWARDS_API_BASE_URL`, `GBREWARDS_SERVICE_TOKEN` | GB Rewards team ([INTEGRATION.md](INTEGRATION.md)) — leave blank while `UNIT_SOURCE_MODE=none` |
   | `SENTRY_DSN` | optional; blank disables Sentry |
   | `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_PASSWORD` | you choose — see §2 |

   `JWT_SECRET` and `DATABASE_URL` are generated by Render; do not set them by
   hand.

4. **Before DLT approval, set `ENV=staging` and leave `SMS_PROVIDER=fake`.** The
   app deliberately refuses to boot with `ENV=prod` and a fake SMS provider —
   that check exists so nobody launches believing customers are being texted when
   they are not. Staging runs identical code and identical checks otherwise:
   every message is written to `sms_messages` and visible, and none is delivered.
   On launch day, flip `ENV=prod` and `SMS_PROVIDER=msg91` in the same change.

5. **Migrations run themselves, once.** `preDeployCommand` runs
   `python -m app.scripts.migrate` in the freshly built image before any new
   instance starts. If it fails, the deploy aborts and the previous version keeps
   serving. It is not in the container start command on purpose — see the comment
   in `backend/Dockerfile`.

6. **Verify.**

   ```bash
   curl -s https://<api-host>/api/v1/healthz    # {"status":"ok"}
   curl -s https://<api-host>/api/v1/readyz     # database/redis/unit_mirror detail
   ```

   `readyz` reporting `unit_mirror: "empty"` is expected before the GB Rewards
   endpoint exists. It is not an error.

**If the service will not boot**, read the logs first: config problems are
deliberately fatal and say exactly what is wrong (`Invalid production config:
...`). The app also opens a database connection at startup to bootstrap the point
rate, so an unreachable database looks like a boot failure rather than a health
check failure.

## 2. Creating the first admin

There is no sign-up screen, by design. The first admin is created from the
environment:

1. Set `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD` in the Render
   dashboard and redeploy (or restart).
2. The next boot creates an **owner** admin if that email does not already exist.
   Look for `bootstrap_admin_created email=...` in the logs.
3. Log in to admin-web with those credentials.
4. **Unset both variables and redeploy.** Leaving a password in the environment
   means the account can be recreated by anyone who can restart the service.

Further admins are created from the admin panel by an owner. Roles:

- `owner` — everything, including changing the point rate and other admins.
- `staff` — day-to-day back office: void, approve, adjust points, allocations.
- `support` — read-mostly: lookup, warranty detail, claims queue. Cannot move
  points or approve backdates. Give this to whoever answers the phone.

## 3. Setting the point rate before launch

**Do this before the first dealer logs in.** A fresh install bootstraps a rate of
**zero** on purpose (see [DECISIONS.md §4](DECISIONS.md)): registrations record
correctly, and nothing pays, until GoodBed decides what a registration is worth.

Admin panel → Points → Set rate, or:

```
POST /api/v1/admin/points/rate     { "points_per_registration": 50, "note": "..." }
```

Setting a rate closes the current version and opens a new one. Ledger entries
keep pointing at the version that produced them, so an entry written before the
change still explains its own amount.

**Registrations made while the rate was zero are not repaid automatically.** If
GoodBed decides to honour them, that is a deliberate act: for each dealer,
Admin → Dealer → Adjust points, `admin_credit` with a reason such as
"programme launch backfill: 12 registrations at 50". The reason is mandatory and
appears in the audit log and on the dealer's own ledger screen.

Rate changes are not retroactive and must not be made so. Re-pricing history
would mean a dealer's statement from last month no longer reconciles.

## 4. Uploading allocations

An allocation is what authorises a dealer to register a serial. Without one, a
scan is refused with `not_allocated`. This upload is therefore both the
anti-abuse gate and the denominator of the compliance report ("allocated 40,
registered 6").

**The file.** CSV with a header row. Column names are matched loosely, because
despatch systems export what they export:

| Meaning | Accepted headers |
|---|---|
| serial (required) | `serial`, `serial_no`, `serial_number`, `serialno`, `unit_serial`, `qr`, `qr_code` |
| dealer (required) | `dealer_code`, `dealercode`, `dealer`, `code`, `dealer_id` |
| despatch reference | `dispatch_ref`, `dispatchref`, `dispatch`, `dispatch_no`, `invoice`, `invoice_ref` |

Dealer codes must already exist — create the dealership first (Admin → Dealers).
Maximum upload size is 10 MB.

**Upload.** Admin → Allocations → Upload, or
`POST /api/v1/admin/allocations/upload` (multipart). The whole file applies in
one transaction: a half-applied despatch file is worse than a rejected one.

**Read the error report.** Every rejected line is named with its line number,
serial and reason. Common ones:

- *unknown dealer code* — create the dealership, then re-upload the same file.
- *already allocated to another dealer* — a serial cannot be in two places. Check
  the despatch data; if the first allocation was wrong, revoke it
  (`POST /api/v1/admin/allocations/{id}/revoke`, reason required) and re-upload.
- *already registered* — the unit has been sold. Nothing to do.

**Re-uploading is safe.** A row already allocated to the same dealer is a no-op
success. Clerks re-send files, append rows to yesterday's export, and forward the
same attachment twice; if that were an error, the operator would learn to ignore
the error report, which is the only valuable part of the screen.

**Revoking** takes a serial away from a dealer (stock returned to the warehouse,
dealer suspended). It cannot revoke a serial that has already been registered —
that is a void, not a revoke, and it involves a customer's warranty.

## 5. When the unit mirror goes stale

**First: nothing is broken for dealers.** A stale or empty mirror does not stop a
single sale. Registration is gated by allocations, not by the mirror. What
degrades is the model name shown at the counter and the warranty term taken from
the unit — a stale-mirror registration falls back to `DEFAULT_WARRANTY_MONTHS`
and is flagged `unit_unverified = true` for reconciliation.

**Diagnose:**

```bash
curl -s https://<api-host>/api/v1/readyz | jq .checks.unit_mirror
# { "last_synced_at": "...", "age_hours": 31.4, "stale": true }
```

```sql
-- how many allocated serials have never been mirrored
SELECT count(*) FROM allocations a
LEFT JOIN units u ON u.serial = a.serial
WHERE a.status IN ('allocated','registered')
  AND (u.id IS NULL OR u.source <> 'gbrewards');
```

**Then work down this list:**

1. **Is `UNIT_SOURCE_MODE=none`?** Then the mirror is empty by design and there is
   nothing to fix. Expected until the GB Rewards endpoint exists.
2. **Did the cron job run?** Render → `dealerrewards-unit-sync` → Events. The job
   exits 0 and logs `sync_skipped` when the integration is disabled, so a green
   run does not always mean data moved. Look for
   `sync_finished ok=… missing=… unavailable=…`.
3. **`unavailable` high, `ok` zero** — GB Rewards is down or the token is wrong.
   Check with a single request:

   ```bash
   curl -i -H "Authorization: Bearer $GBREWARDS_SERVICE_TOKEN" \
     "$GBREWARDS_API_BASE_URL/api/v1/internal/units/<a-known-serial>"
   ```

   401/403 means the token; a timeout means their service. Tell their team; do
   nothing else. Sales continue.
4. **`missing` high** — upstream returns 404 for serials we have allocated. Those
   allocations may be for units that were never manufactured, or a despatch file
   had mistyped serials. Give the list to whoever produces the despatch export.
5. **Force a resync** once upstream is healthy (Render → Shell, or a one-off job):

   ```bash
   python -m app.scripts.sync_units --force --limit 5000
   ```

6. **Reconcile the warranties written during the outage:**

   ```sql
   SELECT id, serial, model_name, warranty_months, registered_at
   FROM warranties WHERE unit_unverified = true ORDER BY registered_at DESC;
   ```

   Once the mirror is repopulated, compare each against the mirrored unit. If the
   term differs, that is a decision for a human, not a script: the warranty was
   sold under the terms printed on the record the customer holds.

## 6. Retrying failed SMS

Every outbound message is a row in `sms_messages` **before** the provider is
called, and the provider's answer is written back onto it. "Did the customer get
the message?" is always answerable.

**Find failures:**

```sql
SELECT id, to_phone, template_key, status, attempts, error, created_at
FROM sms_messages
WHERE status IN ('failed','queued') AND created_at > now() - interval '3 days'
ORDER BY created_at DESC;
```

**Retry** (Render → Shell on the API service, or a one-off job):

```bash
python -m app.scripts.retry_sms --dry-run     # list what would be retried
python -m app.scripts.retry_sms --limit 50    # retry oldest first
python -m app.scripts.retry_sms --message-id <uuid>
```

Messages already attempted five times are skipped unless `--force`. After five
failures the number is usually wrong rather than the network — fix the number
instead (§7), which re-sends on its own.

**Reading the error text:**

- *DLT / template rejected* — the template text or its variables do not match
  what was approved. No amount of retrying fixes this; the template must be
  re-approved. Until then, `SMS_PROVIDER=fake` at least keeps a record of what
  should have gone out.
- *Invalid number* — a typo at the counter. Correct the customer's number (§7).
- *Timeout / 5xx* — the provider. Retry later.

An SMS failure never affects the warranty. It is a notification about a sale that
is already committed, sent outside the transaction on purpose.

## 7. Investigating a disputed warranty

Someone claims a warranty started on the wrong date, or belongs to the wrong
person, or should not exist. Everything you need is on the record; nothing here
requires guessing.

**Start:** Admin → Warranties → search by serial, phone or invoice reference
(`GET /api/v1/admin/warranties?...`, detail at `/warranties/{id}`).

**The five sources of truth, in the order they answer questions:**

| Table | Answers |
|---|---|
| `warranties` | the dates, the terms, who sold it, whether the unit was verified |
| `warranty_events` | every state change, appended, with actor and reason — the DB rejects UPDATE and DELETE on this table |
| `audit_logs` | who did what from the admin side, with a mandatory reason |
| `sms_messages` | what the customer was told, and whether it was delivered |
| `ledger_entries` | what was paid and what was reversed |

```sql
SELECT * FROM warranty_events WHERE warranty_id = '<id>' ORDER BY created_at;
SELECT * FROM audit_logs WHERE entity_id = '<id>' ORDER BY created_at;
```

**Reading the warranty row:**

- `warranty_start_date` is server-derived. If `backdate_days > 0`, the dealer
  supplied an invoice date and pulled it back by that many days; up to seven is
  automatic, beyond that `backdate_approved_by_admin_id` names the approver.
- `source = 'dealer'` means the shop registered it at the counter.
  `customer_self` means the customer registered it themselves later, which is the
  non-compliance case this product exists to reduce — and it pays no points.
- `unit_unverified = true` means the sale completed while GB Rewards was
  unreachable or did not know the serial. It does not mean the sale is fake.
- **Expiry is not stored.** A warranty is expired when
  `warranty_end_date < today`; the status stays `active`. If a row says `active`
  and the end date is in the past, that is correct, not a bug.
- `staff_id` names the individual who scanned, `dealer_id` the shop that was paid.

**Common disputes:**

*"My warranty should have started earlier."* Check `invoice_date` versus
`warranty_start_date` and `backdate_days`. If the dealer registered late and did
not supply the invoice date, the record is accurate about what happened — the
warranty started when it was registered. Correcting it is an admin decision with
a reason, not a support default: the entire product exists because that date was
previously whatever anyone said it was.

*"That is not my mattress."* Look at `sms_messages` for that warranty. If the SMS
was delivered and the customer never disputed it through the support site, the
registration is at least contemporaneous. Then check whether the customer's
details were edited (`audit_logs`, action `edit_customer`) and by whom.

*"This unit is registered to someone else."* Only one live warranty can exist per
serial — the database enforces it. Either the serial was scanned wrongly (check
`warranties.serial` against the label) or the mattress was genuinely sold twice,
which means one of the two sales is fictitious. Voiding the wrong one frees the
serial for the real one.

## 8. A dealer disputing a clawback

A dealer's balance dropped because a warranty was voided. Their points went
negative, or their redemption was refused, and they are on the phone.

**1. Find the pair.** Admin → Dealer → Ledger
(`GET /api/v1/admin/dealers/{id}/ledger`), or:

```sql
SELECT created_at, type, amount, reason, warranty_id
FROM ledger_entries
WHERE dealer_id = '<dealer id>' ORDER BY created_at DESC LIMIT 50;
```

A clawback is a `registration_reversal` for the negative of a
`registration_credit` on the same `warranty_id`. **Both rows are always there.**
Nothing is ever edited or deleted, so "you earned 50 and it was reversed on the
14th, because of X" is a statement you can make with the record open.

**2. Find the reason and the person.** The reason is mandatory and is stored in
three places: on the ledger row, on the warranty event, and in the audit log with
the admin who did it. Read it out. Most disputes end here, because the reason is
usually "customer returned the mattress on 12 March".

**3. If the void was correct**, the clawback stands. The balance may be negative;
that is a debt, and it is deliberate. Refusing to claw back from a dealer who has
already spent the points would make "register fakes, redeem quickly" profitable.
Explain that new registrations pay down the negative balance normally.

**4. If the void was a mistake**, there are two separate things to repair, and it
matters that they are separate:

- **The points.** Admin → Dealer → Adjust points: `admin_credit` for the amount,
  with a reason naming the void it corrects ("reverses erroneous clawback on
  warranty <id>, voided in error on 14 Mar"). Do **not** try to delete the
  reversal; the ledger is append-only and the correction should be visible.
- **The warranty.** Voiding freed the serial, so the dealer can register it
  again — but a fresh registration starts the clock **today**, which would take a
  month off the customer's cover. Have the dealer re-register with the original
  **invoice date**. Because that date is more than seven days old, the warranty
  lands in `pending_backdate`; approve it honouring the requested date
  (`POST /api/v1/admin/approvals/{id}/approve`) and the original start date is
  restored, with the approval recorded against your name.

**5. If the dispute is about which dealer was paid** (two shops claim the same
sale), the allocation record decides. A serial is allocated to exactly one dealer
at a time, and the allocation batch says which despatch file put it there. That
file came from GoodBed's own despatch system, which is a stronger claim than
either shop's memory.

## 9. Incident quick reference

| Symptom | Likely cause | Action |
|---|---|---|
| All registrations return 503 `rate_limit_unavailable` | Redis is down | The limiter fails **closed** on purpose: better to stop paying than to pay without a limit. Restore Redis; nothing is lost. |
| Service will not boot, logs say `Invalid production config` | A required variable is unset for this `ENV` | Read the message — it names each problem. |
| Service will not boot, database errors at startup | Postgres unreachable | The app bootstraps the point rate at startup. Fix connectivity; no data action needed. |
| Dealers get `not_allocated` on everything | Allocation file never uploaded, or uploaded against the wrong dealer codes | §4 |
| `already_registered` for a genuine new sale | The serial carries a live warranty | §7 — one of the two registrations is wrong |
| Customers report no SMS | `SMS_PROVIDER=fake`, or DLT template rejected | §6 |
| Deploy aborted at pre-deploy | A migration failed | The previous version is still serving. Fix the migration; do not bypass the step. |

## 10. Backups: test the restore before you need it

Once, before launch, and then once a quarter:

1. Render → Database → Backups → restore the latest backup into a **new**
   instance.
2. Point a scratch environment at it (`DATABASE_URL` only) and confirm the row
   counts for `warranties`, `ledger_entries` and `allocations` match production.
3. Delete the scratch instance.

A backup that has never been restored is a belief, not a backup. This database is
the only place a five-year warranty obligation is written down.
